# Техническое задание: «Galaxy» — граф социальных связей в виде звёздного неба

Документ предназначен для исполнителя-ИИ. Всё, что описано ниже, — обязательные требования,
если явно не помечено как «опционально». Раздел 7 (математика раскладки) — ядро продукта,
его нельзя упрощать до типового force-directed «как в d3 по умолчанию».

## 1. Суть продукта

Приватный сервис для одного круга общения (владелец + друзья + знакомые + их комьюнити).
Каждый участник — светящаяся звезда на тёмном небе. Дружеские связи — тонкие светящиеся линии.
Чем больше у человека подтверждённых связей, тем ближе его звезда к центру карты.
Несколько «хабов» ведут себя как кратная звёздная система: расталкиваются, но общий центр масс
остаётся в центре экрана.

Вход — только через Telegram, внутри Telegram Mini App. ID пользователя в системе **равен**
его Telegram user id.

Ожидаемый масштаб: **до ~200 пользователей**. Все алгоритмы и рендер проектируются под этот
потолок; оптимизации ради 10 000 узлов делать не нужно и вредно (они съедят качество картинки).

Язык интерфейса: русский. Единственный.

Адрес сервиса: **`https://kvadratnikitosa.ru/galaxy`** — подпуть на уже работающем VPS
владельца, рядом с двумя другими его проектами. Подробности размещения — раздел 2.

### 2.2. Подпуть `/galaxy` — сквозное требование

Приложение живёт **не в корне домена**. Это самая частая причина сломанного деплоя,
поэтому базовый путь задаётся один раз и протягивается через все слои:

```ts
// shared/config.ts — один источник истины, импортируется и клиентом, и сервером
export const BASE_PATH = '/galaxy'
```

Что обязано его учитывать:

| Слой | Требование |
|---|---|
| Vite | `base: '/galaxy/'` в `vite.config.ts` — иначе бандл запросит `/assets/*` и получит чужое приложение |
| Роутер клиента | `basename="/galaxy"` (или ручной разбор `location.pathname` с обрезкой префикса) |
| Клиентский API-клиент | Все запросы идут на `/galaxy/api/...`. Захардкоженных `/api/...` в коде быть не должно |
| Express | `app.use(BASE_PATH, router)` — весь роутер монтируется под префикс |
| Кука сессии | `path=/galaxy` — чтобы не утекала в соседние приложения домена |
| Аватарки | Отдаются по `/galaxy/avatars/<файл>` |
| Вебхук бота | `https://kvadratnikitosa.ru/galaxy/tg/webhook/<secret>` |
| Mini App URL в BotFather | `https://kvadratnikitosa.ru/galaxy` |

Проверка на приёмке: открыть `https://kvadratnikitosa.ru/galaxy` и убедиться, что во вкладке
Network **ни один** запрос не уходит выше префикса `/galaxy/`.

### 2.3. Статику раздаёт Node, не nginx

Так же, как в соседнем проекте `kvadrat`. Это даёт одну-единственную запись в nginx вместо
трёх и убирает возню с `try_files` для SPA внутри подпути.

Express-роутер, порядок маршрутов строго такой:

1. `/galaxy/assets/*` — собранный бандл, `Cache-Control: public, max-age=31536000, immutable`
   (имена файлов Vite уже содержат хеш);
2. `/galaxy/avatars/*` — из `AVATAR_DIR`, тот же `immutable`;
3. `/galaxy/api/*` — API;
4. `/galaxy/tg/webhook/:secret` — вебхук Telegram;
5. всё остальное под `/galaxy` → отдать `public/index.html` с `Cache-Control: no-cache`
   (SPA-фолбэк).

Индекс никогда не кешировать, ассеты — навсегда: иначе после деплоя у людей останется
старый `index.html`, ссылающийся на снесённые бандлы.

### 2.5. Фрагмент nginx (владелец вставляет сам)

Кладём в репозиторий как `deploy/nginx.galaxy.conf`, внутрь существующего
`server { listen 443 ssl; server_name kvadratnikitosa.ru; ... }`:

```nginx
location /galaxy/ {
    proxy_pass http://127.0.0.1:3005;
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Аватарки и бандл отдаёт Node; апстрим ставит свои заголовки кеширования сам.
    proxy_buffering on;

    # Вебхук Telegram может прислать до нескольких сотен килобайт.
    client_max_body_size 2m;
}

# Вход без слеша: /galaxy -> /galaxy/
location = /galaxy {
    return 301 /galaxy/;
}
```

**`proxy_pass` без завершающего слеша** — принципиально: так nginx передаёт исходный URI
целиком, вместе с префиксом `/galaxy`, которого и ждёт Express. Со слешем
(`proxy_pass http://127.0.0.1:3005/;`) префикс будет срезан, и все маршруты отдадут 404.

Отдельно проверить, что в объемлющем `server {}` нет `X-Frame-Options: DENY` и
`frame-ancestors`, запрещающих `https://web.telegram.org` — иначе Mini App не откроется
в веб-клиенте Telegram. Если такие заголовки стоят глобально для домена, внутри
`location /galaxy/` их нужно переопределить.

### 2.6. PostgreSQL на сервере

**На VPS сейчас нет никакой БД вообще** — соседние проекты (`kvadrat`, `bankiru`) хранят
состояние в файлах. Установка и настройка кластера PostgreSQL входит в объём работ и
выполняется с нуля.

Владелец разрешил ставить и использовать БД свободно, поэтому кластер разворачивается как
**общесерверный**, а не как приватная база одного приложения: этой же машиной будут
пользоваться будущие проекты. Отсюда правила, которые нельзя нарушать даже ради удобства:

- Один кластер на весь сервер, отдельные роль и база **на каждый проект**.
  Наш проект получает роль `galaxy` и базу `galaxy`, всё именуется одинаково.
- Приложение **никогда** не подключается суперпользователем `postgres`.
  `DATABASE_URL` содержит только роль `galaxy`, у которой прав ровно на свою базу.
- Наше приложение не считает кластер своей собственностью: не меняет глобальные
  настройки `postgresql.conf` под себя, не создаёт объекты вне схемы `public` базы `galaxy`,
  не трогает чужие базы и роли. Дефолтных настроек PostgreSQL для сотен строк хватает
  с многократным запасом — тюнинг не нужен.

Разовая установка (описать пошагово в `README.md` и выполнять из `./deploy.sh --setup`):

```bash
# Версия — любая из репозитория дистрибутива, но не ниже 14 (требование Prisma).
# Проверить, что предлагает apt, и поставить её:
apt-get update && apt-get install -y postgresql postgresql-contrib
psql --version

systemctl enable --now postgresql
```

Кластер создаётся установщиком автоматически. Убедиться, что он в UTF-8:

```bash
sudo -u postgres psql -c "SHOW server_encoding;"   # ожидаем UTF8
```

Роль и база под проект:

```bash
sudo -u postgres psql -c "CREATE ROLE galaxy LOGIN PASSWORD '<пароль>';"
sudo -u postgres psql -c "CREATE DATABASE galaxy OWNER galaxy ENCODING 'UTF8';"
```

Пароль генерировать `openssl rand -base64 24`, вписывать в `.env` и больше нигде
не хранить — ни в репозитории, ни в скриптах деплоя.

**Доступ только с localhost.** Проверить, что `listen_addresses = 'localhost'`
(значение по умолчанию) и что в `pg_hba.conf` нет строк с внешними подсетями.
Порт 5432 наружу не открывать — приложение ходит через `127.0.0.1`. Если на сервере
включён firewall, убедиться, что 5432 в нём закрыт.

Проверка, что всё поднялось, до первого деплоя:

```bash
psql "postgresql://galaxy:<пароль>@127.0.0.1:5432/galaxy" -c "SELECT 1;"
```

**Права и миграции.** На проде выполняется только `npx prisma migrate deploy` — ему
достаточно прав владельца базы, теневая база не нужна. Атрибут `CREATEDB` роли `galaxy`
на сервере не выдавать. Локально, где разработчик гоняет `prisma migrate dev`, нужна
теневая база — там роль заводится с `CREATEDB`, и это различие между локалью и продом
должно быть явно описано в `README.md`, иначе `migrate dev` на проде однажды запустят
и получат невнятную ошибку прав.

**Резервные копии.** Крон раз в сутки:

```
0 4 * * * pg_dump -Fc "postgresql://galaxy:<пароль>@127.0.0.1:5432/galaxy" \
  > /root/backups/galaxy-$(date +\%F).dump 2>>/root/backups/galaxy-backup.log
```

Хранить 14 последних, старые удалять. Дамп делать по базе `galaxy`, а не по всему кластеру:
когда на сервере появятся другие проекты, их бэкапы должны быть независимы от нашего.
База маленькая (сотни строк), дамп занимает секунды. В `README.md` описать и обратную
операцию — восстановление `pg_restore` в чистую базу, вместе с порядком: погасить `galaxy`
в pm2, восстановить, поднять обратно.

### 2.7. Переменные окружения

Файл `/root/dev/galaxy/dist/.env` создаётся на сервере вручную один раз и **исключён
из rsync** — деплой его не перетирает и не удаляет.

```
DATABASE_URL=postgresql://galaxy:***@127.0.0.1:5432/galaxy
PORT=3005
PUBLIC_BASE_URL=https://kvadratnikitosa.ru/galaxy
TELEGRAM_BOT_TOKEN=123456:AA...
TELEGRAM_BOT_USERNAME=galaxy_constellation_bot
TELEGRAM_WEBHOOK_SECRET=<случайные 32 байта hex>
SESSION_SECRET=<случайные 32 байта hex>
ADMIN_TELEGRAM_IDS=111111111,222222222
AVATAR_DIR=/root/dev/galaxy/avatars
LAYOUT_RECOMPUTE_DEBOUNCE_MS=4000
```

`AVATAR_DIR` лежит **рядом с `dist`, а не внутри него**: `rsync --delete` вычистил бы
загруженные аватарки при каждом деплое.

`env.ts` пишется руками, без библиотек валидации: читает `process.env`, проверяет наличие
обязательных ключей, приводит числа через `Number()` с проверкой на `NaN`, разбирает
`ADMIN_TELEGRAM_IDS` в массив `BigInt`, и при первой же проблеме падает на старте с
сообщением вида `Не задана переменная окружения TELEGRAM_BOT_TOKEN`. Экспортирует
замороженный типизированный объект. Падать нужно именно на старте, а не при первом
запросе, — тогда pm2 сразу покажет проблему в логе.

### 2.8. Валидация входных данных без библиотек

`zod` исключён. Вместо него — `server/src/lib/validate.ts`: набор маленьких функций,
каждая либо возвращает приведённое значение, либо бросает `BadRequest` с кодом поля.

```ts
class BadRequest extends Error { constructor(public field: string, public code: string) { … } }

function str(v: unknown, field: string, opts: { min?: number; max?: number; trim?: boolean }): string
function int(v: unknown, field: string, opts: { min?: number; max?: number }): number
function bigint(v: unknown, field: string): bigint        // принимает строку, отвергает нечисловое
function oneOf<T extends string>(v: unknown, field: string, allowed: readonly T[]): T
function optional<T>(v: unknown, fn: () => T): T | null    // null/undefined -> null
```

Правила:
- Каждый маршрут разбирает тело **явно**, поле за полем, в начале обработчика.
  Никаких `req.body as SomeType` — это не валидация, а её имитация.
- Неизвестные поля в теле игнорируются молча.
- `BadRequest` перехватывается общим обработчиком ошибок и превращается в `400`
  с `{ "error": { "code": "invalid_field", "message": "…", "field": "age" } }`.
- Числовые границы и правила для каждого поля — в разделах 5 и 10, они нормативные.

## 3. Модель данных (Prisma)

```prisma

  linksB            Link[]   @relation("LinkB")

  bId         BigInt

  @@index([aId]) @@index([bId])

// Приглашение = «тусклая точка». Видна ТОЛЬКО пригласившему.
model Invite {
  id             String       @id @default(cuid())

  inviterId      BigInt
  inviter        User         @relation("Inviter", fields: [inviterId], references: [id], onDelete: Cascade)
  label          String?                    // как пригласивший подписал точку: «Вася с работы»
  status         InviteStatus @default(PENDING)
  acceptedById   BigInt?
  acceptedBy     User?        @relation("Acceptor", fields: [acceptedById], references: [id], onDelete: SetNull)
  createdAt      DateTime     @default(now())
  acceptedAt     DateTime?

  @@index([inviterId, status])
}

// Исходящие сообщения бота. Нужен, потому что отправка может упасть
// (пользователь не начинал диалог с ботом или заблокировал его).
model BotOutbox {
  id         String       @id @default(cuid())
  userId     BigInt
  kind       String                          // "invite_accepted" | "linked"
  text       String
  status     OutboxStatus @default(QUEUED)
  attempts   Int          @default(0)
  lastError  String?
  createdAt  DateTime     @default(now())
  sentAt     DateTime?

  @@index([status, createdAt])
}

model AdminAudit {
  id        String   @id @default(cuid())
  adminId   BigInt
  action    String                           // "rename" | "delete_user" | "create_test" | ...
  targetId  String
  details   Json?
  createdAt DateTime @default(now())
}

model LayoutState {
  id          Int      @id @default(1)       // singleton-строка
  version     Int      @default(0)
  computedAt  DateTime @default(now())
  params      Json                           // снимок коэффициентов из раздела 7
  dirty       Boolean  @default(false)
}
```

`BigInt` в JSON не сериализуется — во всех ответах API id отдаются **строками**.
Сделать один хелпер сериализации и использовать его везде.

## 4. Аутентификация через Telegram Mini App

### 4.1. Проверка initData — реализовать точно так

Клиент при старте берёт `window.Telegram.WebApp.initData` (это строка вида query-string) и
отправляет её в `POST /api/auth/telegram`. Сервер:

1. Разбирает строку в пары ключ-значение.
2. Извлекает и удаляет поле `hash`.
3. Оставшиеся пары сортирует по ключу и склеивает в `data_check_string` через `\n`
   в формате `key=value`.
4. Считает `secret_key = HMAC_SHA256(key="WebAppData", message=BOT_TOKEN)`.
5. Считает `computed = HMAC_SHA256(key=secret_key, message=data_check_string)` в hex.
6. Сравнивает `computed` с `hash` **через `crypto.timingSafeEqual`**.
7. Проверяет `auth_date`: отвергнуть, если старше 24 часов.

Порядок аргументов HMAC на шаге 4 — частая ошибка: ключ именно строка `"WebAppData"`,
сообщение — токен бота. Не наоборот. Ошибка на любом шаге → `401`, без подробностей в теле.

### 4.2. Сессия

При успехе сервер выставляет httpOnly-куку `gx_session` с JWT (HS256, `SESSION_SECRET`,
срок 30 дней). Payload: `{ sub: "<telegram id>", iat, exp }`.

Атрибуты куки — все три обязательны и ни один нельзя опустить:

```
HttpOnly; Secure; SameSite=None; Path=/galaxy; Max-Age=2592000
```

`SameSite=None` — иначе кука не переживёт iframe Telegram. `Path=/galaxy` — чтобы она
не уходила в соседние приложения того же домена (`/` и `/bankiru`), которым знать о нашей
сессии незачем. Клиент обязан слать запросы с `credentials: 'include'`.
Все остальные эндпоинты авторизуются по этой куке. Заголовок с initData на каждый запрос
не гонять.

### 4.3. Создание и обновление профиля при входе

Из `initData.user` берём `id`, `first_name`, `last_name`, `username`, `language_code`,
`photo_url`. **Ни возраста, ни пола Telegram не отдаёт** — эти поля заполняет только сам
пользователь в приложении.

- Пользователя нет → создаём, ставим `createdAt`.
- Пользователь есть → обновляем telegram-поля и `lastSeenAt`.
- `isBlocked = true` → `403` и экран «доступ закрыт».
- Если `photo_url` есть и `avatarFetchedAt` старше 7 дней (или пусто) → ставим задачу
  на обновление аватарки (раздел 9), но **не блокируем ответ**.

### 4.4. Отображаемое имя — каскад

Функция `displayName(user)` на сервере, единственный источник истины, клиент имя не вычисляет:

1. `customName`, если не пусто;
2. иначе `telegramFirstName + " " + telegramLastName` (склейка непустых, trim);
3. иначе `"@" + telegramUsername`;
4. иначе `String(id)`.

## 6. Связи и приглашения

### 6.1. Три способа появления связи

1. **Приглашение по ссылке.** Пользователь жмёт «Позвать друга», опционально вписывает подпись
   («Вася с работы»), сервер создаёт `Invite` с токеном. На небе у пригласившего появляется
   тусклая точка, соединённая с ним пунктиром. Точку видит **только пригласивший**.
   Когда приглашённый открывает ссылку и входит — связь создаётся автоматически,
   отдельного подтверждения не требуется, звезда загорается.
2. **Кнопка «Связать» на карте.** Любой пользователь может выбрать любую чужую звезду и
   нажать «Связать» — связь создаётся мгновенно, без подтверждения второй стороны.
   Второй стороне уходит уведомление от бота, и она может в любой момент «Развязать».
3. **Админка.** Владелец вручную создаёт и удаляет любые связи между любыми пользователями
   (сценарий холодного старта: небо уже обжито к моменту, когда зайдут первые друзья).

### 6.2. Ссылка-приглашение

Формат: `https://t.me/<TELEGRAM_BOT_USERNAME>?startapp=<token>`

Параметр `startapp` приходит в Mini App как `initData.start_param`. Использовать именно
`startapp` (открывает Mini App сразу), а не `start` (открывает чат с ботом).

`POST /api/invites` возвращает `{ id, token, url, shareText }`. `shareText` — готовый текст:

> Привет! Я собираю карту своих друзей и знакомых — она выглядит как звёздное небо,
> где каждый человек звезда, а знакомства — линии между ними. Открой ссылку, и рядом
> с моей звездой загорится твоя.

В Mini App кнопка «Отправить другу» вызывает:

```ts
Telegram.WebApp.openTelegramLink(
  "https://t.me/share/url?url=" +
    encodeURIComponent(url) +
    "&text=" +
    encodeURIComponent(shareText),
);
```

Плюс кнопка «Скопировать ссылку» как запасной вариант.

### 6.3. Приём приглашения — алгоритм и крайние случаи

При `POST /api/auth/telegram`, если в initData есть `start_param`, после создания/обновления
пользователя в **одной транзакции**:

1. Найти `Invite` по токену. Нет или `status != PENDING` → просто залогинить, ничего не делать.
2. `invite.inviterId === user.id` → не создавать связь на себя; пометить `REVOKED`.
3. Нормализовать пару `(a, b) = (min, max)`. Если `Link` уже есть → пометить приглашение
   `ACCEPTED`, дубль не создавать.
4. Иначе создать `Link` с `createdById = inviterId`, пометить `Invite.ACCEPTED`,
   проставить `acceptedById`, `acceptedAt`.
5. Поставить в `BotOutbox` уведомление пригласившему.
6. Пометить `LayoutState.dirty = true`.

Токен одноразовый. Ограничение: не более 50 приглашений в статусе `PENDING` на пользователя.

### 6.4. «Связать» / «Развязать»

- `POST /api/links` `{ targetId }` — создать связь текущего пользователя с целевым.
  Ошибки: связь с самим собой, цель не существует, цель заблокирована, связь уже есть (`409`),
  превышен лимит (200 связей на пользователя).
  Успех → уведомление в `BotOutbox` цели: «X отметил(а) знакомство с тобой на карте».
- `DELETE /api/links/:targetId` — удалить связь. Может любая из двух сторон.
  Уведомление при разрыве **не отправляется** (намеренно: разрыв связи — приватное действие).
- Оба действия помечают `LayoutState.dirty = true`.

Дубликаты исключены на уровне БД (`@@unique([aId, bId])` + инвариант `aId < bId`).
Один человек, приглашённый тремя людьми, — это одна звезда с тремя линиями.

## 7. Математика раскладки (ядро)

Цель: воспроизвести поведение звёздной системы.

- Больше подтверждённых связей → ближе к центру.
- Один хаб → он в центре.
- Два сопоставимых хаба → расходятся симметрично, центр карты оказывается между ними.
- Три и более → правильная конфигурация вокруг общего центра масс.
- Небо не должно перетасовываться при каждом заходе: раскладка стабильна.

Раскладка считается **на сервере**, координаты пишутся в `User.x/y`. Клиент только
анимирует небольшие колебания вокруг них (раздел 8.4).

Все коэффициенты вынести в один файл `layout/params.ts` с комментариями — их придётся крутить.

### 7.1. Центральность

Только подтверждённые связи (таблица `Link`), тестовые пользователи участвуют наравне.

1. Степень `deg_i` — число связей.
2. Собственная центральность `e_i` — степенной метод по матрице смежности:
   - `e ← 1/n` для всех, затем 100 итераций `e'_i = Σ_{j∈N(i)} e_j`, после каждой —
     нормировка `e ← e / ||e||₂`. Изолированные узлы дадут 0, это нормально.
3. Нормировать обе величины в `[0,1]` по min-max (если max == min → все 0).
4. Итог: `c_i = 0.7 · deg̃_i + 0.3 · ẽ_i`, затем ещё раз min-max в `[0,1]` → `ĉ_i`.

Почему не только степень: человек с пятью связями внутри плотного комьюнити и человек с пятью
связями со случайными одиночками — это разное положение в социальной ткани. Вес 0.7 у степени
сохраняет главное правило заказчика («больше друзей → ближе к центру»), а собственная
центральность работает разрешителем ничьих. Веса вынести в параметры.

Записать `ĉ_i` в `User.centrality`, `deg_i` в `User.degree`.

### 7.2. Масса и целевой радиус

```
m_i = 1 + deg_i
r_target_i = R_MAX · (1 − ĉ_i)^0.5          // R_MAX = 1000 условных единиц
```

Показатель 0.5 даёт равномерную плотность звёзд по площади: без него периферия
получается разреженной, а центр слипается.

### 7.3. Силы

Центр `C` зафиксирован в `(0,0)` на время симуляции. `û_i` — единичный вектор от `C` к `p_i`,
`d_ij` — расстояние между узлами, `û_ij` — единичный вектор от `j` к `i`.

**Радиальная привязка** (тянет узел на его целевую орбиту):

```
F_rad_i = −K_RAD · m_i · (|p_i − C| − r_target_i) · û_i          K_RAD = 0.08
```

Множитель `m_i` — тяжёлые узлы держат свою орбиту жёстче лёгких.

**Отталкивание** (кулоновское, по всем парам; при n ≤ 200 прямой перебор O(n²) —
это ~20 000 пар на итерацию, быстрее любого Barnes-Hut, аппроксимации не нужны):

```
F_rep_ij = K_REP · m_i · m_j / max(d_ij², D_MIN²) · û_ij         K_REP = 900, D_MIN = 14
```

**Пружины на рёбрах**:

```
L_ij = L0 · (1 + 0.18 · (√m_i + √m_j))                           L0 = 55
F_spr_ij = −K_SPR · (d_ij − L_ij) · û_ij                         K_SPR = 0.035
```

Зависимость длины ребра от масс даёт хабам пространство вокруг себя, иначе их соседи
слипаются в комок.

**Интегрирование** (полуявный Эйлер с охлаждением):

```
v_i ← (v_i + (ΣF_i / m_i) · DT) · DAMPING                        DT = 1.0, DAMPING = 0.88
p_i ← p_i + v_i · α
α   ← α · COOLING                                                COOLING = 0.985
```

Деление на `m_i` — тяжёлые узлы инертны, мелочь крутится вокруг них. Это и даёт визуальное
ощущение звёздной системы.

**Жёсткое разведение** после каждого шага: если `d_ij < radius_i + radius_j + 6`, раздвинуть
пару на половину недостачи каждую, обратно пропорционально массам.

Остановка: `α < 0.005` либо 800 итераций.

### 7.4. Почему это даёт двойную звезду

Для двух равных хабов `m₁ = m₂ = m`, у обоих `ĉ = 1`, значит `r_target = 0`.
Симметрично относительно `C` на расстоянии `d/2` каждый, баланс вдоль линии между ними:

```
K_RAD · m · (d/2) = K_REP · m² / d²    ⟹    d = ∛(2 · K_REP · m / K_RAD)
```

То есть два хаба расходятся на конечное расстояние, растущее с их массой, а середина между
ними остаётся в центре карты — ровно та картина, которая нужна. Один хаб: отталкивание от
множества периферийных узлов гасится по симметрии, узел садится в центр.
**Оба сценария обязаны быть покрыты тестами (раздел 13).**

### 7.5. Детерминизм и начальные позиции

Никакого `Math.random()` в раскладке. Использовать seeded PRNG `mulberry32(seed)` c
`seed = 0x9E3779B9` из `layout/params.ts`.

Первичная раскладка (позиций в БД нет): узлы сортируются по `ĉ` по убыванию и
раскладываются подсолнухом по золотому углу — так хабы сразу оказываются в центре,
симуляция сходится за считанные сотни итераций:

```
φ = π · (3 − √5)
p_k = R_MAX · √((k + 0.5)/n) · (cos(kφ), sin(kφ))
```

### 7.6. Инкрементальный пересчёт

Небо не должно перетасовываться каждый раз, когда кто-то добавил одного друга.

- Существующие узлы стартуют со своих сохранённых `x/y`.
- Новый узел ставится рядом с тем, кто его пригласил (или с первым соседом):
  `p_new = p_anchor + 26 · (cos θ, sin θ)`, где `θ` — из seeded PRNG по id нового узла.
  Если якоря нет — по формуле подсолнуха на своё место.
- `α₀ = 0.25`, максимум 200 итераций.
- Полный пересчёт (`α₀ = 1`, 800 итераций) — только по кнопке в админке и при первом запуске.

### 7.7. Нормализация и выравнивание по предыдущему небу

После симуляции:

1. Сдвинуть так, чтобы **взвешенный по массам центроид** оказался в `(0,0)`.
2. Отмасштабировать так, чтобы 95-й процентиль радиусов равнялся `R_MAX`.
3. **Выравнивание (2D-Прокруст / Кабш).** Симуляция свободна относительно поворота и
   отражения: без этого шага небо после пересчёта окажется перевёрнутым, и люди
   перестанут узнавать свою картину. По узлам, присутствующим в обеих раскладках
   (`p` — новая, `q` — предыдущая, вес `w_i = m_i`), найти оптимальный поворот:

   ```
   num = Σ w_i (x_i·qy_i − y_i·qx_i)
   den = Σ w_i (x_i·qx_i + y_i·qy_i)
   θ   = atan2(num, den)
   ```

   Затем посчитать невязку `Σ w_i |R(θ)p_i − q_i|²` для исходной раскладки и для отражённой
   по оси Y (со своим отдельно посчитанным `θ`), применить вариант с меньшей невязкой.
   При первой раскладке шаг пропускается.

4. Записать `x/y` всем пользователям, инкрементировать `LayoutState.version`,
   сбросить `dirty`.

### 7.8. Когда пересчитывать

Любое изменение графа ставит `LayoutState.dirty = true`. Отдельный таймер в процессе
(`setInterval`, 1 с) видит флаг и через `LAYOUT_RECOMPUTE_DEBOUNCE_MS` после **последнего**
изменения запускает инкрементальный пересчёт. Пересчёты не должны накладываться:
простой булев мьютекс в памяти процесса (процесс pm2 один, этого достаточно).

Приглашения (тусклые точки) в физике **не участвуют**. Их позиция вычисляется на клиенте:
вокруг пригласившего по кругу радиуса `52 px`, угол — детерминированно из хеша токена,
чтобы точка не прыгала между заходами.

## 8. Рендер: звёздное небо

Canvas 2D, один `requestAnimationFrame`-цикл, учёт `devicePixelRatio`.
При 200 узлах картинка обязана держать 60 fps на среднем телефоне.

### 8.1. Фон

Вертикальный градиент `#04060E → #0A0E1C → #060811`. Поверх — декоративная звёздная пыль:
600 точек радиусом 0.4–1.1 px со случайной (но seeded) яркостью 0.05–0.25, отрисованные
**один раз** в offscreen-канвас и дальше просто копируемые. Пыль движется с параллаксом
0.25 от камеры. Это фон, а не пользователи — по ней нельзя кликнуть.

Опционально: одна-две крайне тусклые туманности — радиальные градиенты `#1B2A55` и `#3A1E44`
с альфой ≤ 0.10, радиусом ~40% экрана. Аккуратно: небо должно остаться тёмным.

### 8.2. Цвет и размер звезды

```
radius_i  = clamp(1.8 + 2.2 · √deg_i, 1.8, 14)          // в мировых единицах
glow_i    = radius_i · 4.5
bright_i  = 0.55 + 0.45 · ĉ_i
```

Палитра:

- ядро всегда почти белое: `#F4F8FF`;
- базовый ореол: `#C8D8FF`;
- `MALE` → ореол смешать с `#6FA8FF` на **35%**;
- `FEMALE` → ореол смешать с `#FF8FC0` на **30%**;
- `UNSPECIFIED` → без примеси.

Оттенок обязан читаться как намёк, а не как раскраска: рядом стоящие мужская и женская звёзды
отличаются заметно, но в общем плане небо остаётся серебристо-белым. Если при проверке
картинка выглядит как «синие и розовые шарики» — примесь уменьшить.

Заблокированный пользователь (`isBlocked`): звезда серая `#4B5563`, без свечения, альфа 0.35.

### 8.3. Техника свечения

Рисовать сотни радиальных градиентов каждый кадр нельзя. Вместо этого:

1. При старте и при изменении палитры создать спрайты свечения: для каждого сочетания
   (цвет ореола × округлённый размер из ~12 ступеней) отрисовать в offscreen-канвас
   радиальный градиент от `rgba(color, 0.9)` в центре к `rgba(color, 0)` на краю.
2. В кадре рисовать спрайты через `ctx.globalCompositeOperation = 'lighter'` —
   пересекающиеся ореолы складываются, как настоящий свет.
3. Ядро — маленькая заливка `#F4F8FF` поверх, обычным режимом.
4. Спрайты пересоздавать при изменении `devicePixelRatio` и при зуме, пересекающем
   границу ступени (не каждый кадр).

Порядок отрисовки: фон → пыль → рёбра → ореолы → ядра → подписи.

### 8.4. Анимация

Звёзды стоят на серверных координатах, но небо должно дышать:

- **Дрейф:** `offset_i = A_i · (sin(ω_i·t + φ_i), sin(ω'_i·t + ψ_i))`, где
  `A_i = 6 / (1 + 0.35·deg_i)` px (хабы почти неподвижны, периферия плавает сильнее),
  периоды 8–20 с, фазы — из seeded PRNG по id. Амплитуда меньше расстояния между
  соседями, наложений не возникает.
- **Мерцание:** яркость домножается на `1 + 0.10·sin(ω_tw·t + φ_tw)`, период 3–7 с.
- **Появление новой звезды:** вспышка — за 900 мс радиус и свечение идут
  `0 → 1.8× → 1×` с easing `easeOutBack`, одновременно от пригласившего к ней
  «прочерчивается» линия за 400 мс.
- **Переезд при пересчёте раскладки:** интерполяция старых координат в новые за 1200 мс
  с `easeInOutCubic`. Никаких телепортаций.
- При `prefers-reduced-motion: reduce` — отключить дрейф и мерцание, оставить переходы.

### 8.5. Камера

Панорамирование перетаскиванием и одним пальцем, зум колесом и щипком, диапазон 0.35×–4×.
Двойной тап/клик — плавно центрировать на звезде под курсором. Кнопка «Найти меня» —
вернуться к собственной звезде. Границы панорамирования — bounding box графа + 30% запаса.

Инерция после отпускания: скорость затухает с коэффициентом 0.92 за кадр.

### 8.6. Подписи

Показывать имя под звездой только когда: зум ≥ 1.2 **и** (`deg_i ≥ 4` или узел в подсветке
или это сам пользователь). Иначе подписи превращают небо в свалку.
Шрифт 11 px, цвет `rgba(233,240,255,0.75)`, лёгкая тень для читаемости поверх свечений.

### 8.7. Наведение, выбор и карточка

Хит-тест: линейный перебор с запасом `radius_i + 8` px — при n ≤ 200 это дёшево.

- **Десктоп:** наведение → предпросмотр карточки; клик → карточка закрепляется.
- **Мобильные:** наведения нет. Тап по звезде → карточка; тап по пустоте → снять.

Карточка — **в углу экрана** (десктоп: левый нижний, фиксированная, ~300 px;
мобильные: нижняя панель на всю ширину, поверх карты). Содержит:

- аватарку 48×48 (или кружок с первой буквой имени в цвете пола, если аватарки нет);
- имя;
- возраст, если указан;
- «друзей: N»;
- пометку «тестовая», если `isTest`;
- **кнопку «Связать»**, если связи с текущим пользователем нет;
- **кнопку «Развязать»**, если связь есть;
- для тусклой точки-приглашения: подпись, дату, кнопки «Отправить ещё раз» и «Убрать».

Карточки не должно быть для самого себя — вместо кнопок «Редактировать профиль».

Подсветка при выборе: выбранная звезда и её соседи сохраняют полную яркость, инцидентные
рёбра усиливаются до альфы 0.5, всё остальное затухает до 35% за 200 мс.

### 8.8. Рёбра

- Подтверждённые: линейный градиент между цветами ореолов концов, альфа 0.22, ширина 0.8 px,
  режим `lighter`.
- Пунктир к тусклой точке: `setLineDash([3, 4])`, цвет `#6B7280`, альфа 0.25.
- Тусклая точка: серый круг радиусом 2.5 px, без ореола, альфа пульсирует 0.35 ↔ 0.55
  с периодом 3 с.

## 9. Аватарки

Telegram отдаёт `photo_url` в `initData.user` не всегда (зависит от настроек приватности) —
отсутствие аватарки обязано корректно обрабатываться, а не ломать экран.

Пайплайн:

1. При входе, если `photo_url` есть и `avatarFetchedAt` пуст или старше 7 дней —
   поставить задачу в память процесса (простая очередь с параллелизмом 2).
2. Скачать с таймаутом 5 с и лимитом 2 МБ.
3. `sharp`: resize 64×64 `cover`, `webp({ quality: 80 })` → ~2–4 КБ.
4. Сохранить как `<AVATAR_DIR>/<id>-<sha1(содержимого).slice(0,8)>.webp`,
   записать имя в `User.avatarFile`, удалить предыдущий файл.
5. Ошибка любого шага — залогировать и оставить `avatarFile = null`. Не ретраить в цикле.

Отдача: маршрут `GET /galaxy/avatars/:file` в Express через `express.static(AVATAR_DIR)`
с `Cache-Control: public, max-age=31536000, immutable` (имя содержит хеш содержимого,
инвалидация — сменой имени). Имя файла обязательно проверять регуляркой
`^-?\d+-[0-9a-f]{8}\.webp$` до обращения к диску — путь приходит из URL,
и без проверки это дыра на обход каталога.

`AVATAR_DIR` лежит вне `dist` (`/root/dev/galaxy/avatars`) и не затрагивается деплоем.
Каталог создаётся на старте процесса, если его нет.

Загрузка на клиенте: `GET /galaxy/api/graph` отдаёт имя файла каждого узла. После первой отрисовки
карты (не до неё) клиент фоново, порциями по 8, прогревает все аватарки через `new Image()`.
На 200 пользователей это ~600 КБ суммарно, к первому наведению всё уже в кеше браузера.
Спиннеров и lazy-load не нужно; base64 внутрь JSON не класть — раздувает ответ на треть
и не кешируется отдельно.

## 10. API

**Все пути в таблицах ниже указаны относительно `BASE_PATH`.** Реальный URL получается
приписыванием префикса: `/api/graph` → `https://kvadratnikitosa.ru/galaxy/api/graph`.
В коде роутер монтируется один раз (`app.use(BASE_PATH, router)`), внутри маршрутов
префикс не дублируется; на клиенте URL собирается единственным хелпером в `web/src/api/`.

Все ответы — JSON. Ошибки единым форматом:
`{ "error": { "code": "...", "message": "...", "field": "..." } }` (`field` — только для `400`).
Все id — строки. Все входные тела разбираются вручную через `lib/validate.ts` (раздел 2.8):
библиотек схемной валидации в проекте нет.

### Публичные

| Метод  | Путь                 | Описание                                                                                                             |
| ------ | -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `POST` | `/api/auth/telegram` | Тело `{ initData: string }`. Проверка по 4.1, вход, обработка `start_param`. Ставит куку. Ответ: профиль + `isAdmin` |
| `POST` | `/api/auth/logout`   | Удаляет куку                                                                                                         |

### Пользовательские (нужна сессия)

| Метод    | Путь                   | Описание                                                |
| -------- | ---------------------- | ------------------------------------------------------- |
| `GET`    | `/api/me`              | Профиль, `isAdmin`, `needsProfileSetup`                 |
| `PATCH`  | `/api/me`              | `{ displayName?, age?, gender? }` по правилам раздела 5 |
| `DELETE` | `/api/me`              | Удаление своего профиля                                 |
| `GET`    | `/api/graph`           | Весь граф (см. ниже)                                    |
| `POST`   | `/api/invites`         | `{ label? }` → `{ id, token, url, shareText }`          |
| `GET`    | `/api/invites`         | Свои приглашения в статусе `PENDING`                    |
| `DELETE` | `/api/invites/:id`     | Отозвать (`REVOKED`), тусклая точка исчезает            |
| `POST`   | `/api/links`           | `{ targetId }` — «Связать»                              |
| `DELETE` | `/api/links/:targetId` | «Развязать»                                             |

`GET /api/graph` — единственный тяжёлый запрос, формат:

```jsonc
{
  "layoutVersion": 42,
  "me": "111111111",
  "nodes": [
    {
      "id": "111111111",
      "name": "Аня",
      "gender": "FEMALE",
      "age": 27,
      "degree": 7,
      "centrality": 0.83,
      "x": -120.4,
      "y": 311.9,
      "avatar": "111111111-a1b2c3d4.webp",
      "isTest": false,
      "isBlocked": false,
    },
  ],
  "edges": [["111111111", "222222222"]],
  "pending": [
    {
      "id": "clx...",
      "label": "Вася с работы",
      "createdAt": "2026-09-13T10:00:00Z",
    },
  ],
}
```

`pending` содержит **только приглашения текущего пользователя** — чужие тусклые точки
не отдаются никогда, даже админу в обычном режиме карты.
`edges` — только подтверждённые связи, видны всем.
Ответ кешируется на клиенте; поллинг `GET /api/graph` раз в 30 секунд, плюс немедленный
перезапрос после любого своего действия. WebSocket и SSE **не делать** — на таком масштабе
это лишняя сложность.

### Админские (сессия + id в `ADMIN_TELEGRAM_IDS`)

| Метод    | Путь                          | Описание                                                                                        |
| -------- | ----------------------------- | ----------------------------------------------------------------------------------------------- |
| `GET`    | `/api/admin/users`            | Полный список со всеми полями, счётчиками связей и приглашений                                  |
| `POST`   | `/api/admin/users`            | Создать тестового: `{ name, age?, gender? }`                                                    |
| `PATCH`  | `/api/admin/users/:id`        | `{ displayName?, age?, gender?, isBlocked? }`; переименование ставит `nameLockedByAdmin = true` |
| `DELETE` | `/api/admin/users/:id`        | Удалить пользователя каскадом                                                                   |
| `POST`   | `/api/admin/links`            | `{ aId, bId }` — создать связь между любыми двумя                                               |
| `DELETE` | `/api/admin/links`            | `{ aId, bId }` — удалить связь                                                                  |
| `GET`    | `/api/admin/invites`          | Все приглашения с их статусами                                                                  |
| `POST`   | `/api/admin/layout/recompute` | Полный пересчёт с нуля (`α₀ = 1`, 800 итераций)                                                 |
| `GET`    | `/api/admin/audit`            | Журнал действий, последние 200                                                                  |

Каждое админское изменение пишется в `AdminAudit`.

Проверка прав — в middleware, отдельно на каждом маршруте. Клиентское «не показывать кнопку»
защитой не считается.

### Бот

`POST /tg/webhook/:secret` (полностью: `https://kvadratnikitosa.ru/galaxy/tg/webhook/<secret>`)
— вебхук Telegram, `:secret` сверяется с `TELEGRAM_WEBHOOK_SECRET`
через `timingSafeEqual`, несовпадение → `404`.

Обрабатывать нужно только `/start`: ответить коротким приветствием и кнопкой
`web_app` со ссылкой на Mini App. Остальные апдейты игнорировать с `200 OK`.

## 12. Бот и уведомления

Бот шлёт только два типа сообщений, никаких напоминаний и дайджестов:

1. `invite_accepted` — пригласившему: «🌟 <Имя> принял(а) приглашение — рядом с твоей
   звездой загорелась новая.»
2. `linked` — второй стороне, когда её связали кнопкой: «✨ <Имя> отметил(а) знакомство
   с тобой на карте.»

Отправка идёт **только** через `BotOutbox`: воркер (`setInterval`, 5 с) берёт до 20 записей
`QUEUED`, шлёт `sendMessage`, помечает `SENT`. При ошибке — `attempts++`, экспоненциальная
пауза, после 3 попыток `FAILED` с текстом ошибки.

Отдельно обработать `403 Forbidden: bot was blocked by the user` и «пользователь не начинал
диалог с ботом» — это не сбой, помечать `FAILED` сразу без ретраев. Поскольку пользователи
приходят в Mini App по ссылке через бота, у большинства диалог уже начат, но гарантии нет,
и падать из-за этого приложение не должно.

Все сообщения — `parse_mode: "HTML"`, имя пользователя экранировать.

## 13. Тесты

Обязательный минимум, `vitest`:

**Раскладка (`server/src/layout/*.test.ts`) — самое важное:**

1. «Одна звезда»: граф-звезда (1 хаб + 12 листьев) → расстояние хаба от центра
   меньше 8% от `R_MAX`.
2. «Двойная звезда»: два хаба по 12 листьев каждый, между собой не связаны →
   оба на расстоянии от центра в пределах ±15% друг от друга, а взвешенный по массам
   центроид всей системы — в пределах 5% от `R_MAX` от центра.
3. «Монотонность»: в случайном (seeded) графе из 60 узлов корреляция Спирмена между
   степенью и расстоянием до центра ≤ −0.6.
4. «Детерминизм»: два прогона на одних данных дают идентичные координаты до 1e-9.
5. «Стабильность»: добавление одного узла к готовой раскладке из 100 сдвигает
   медианный узел меньше чем на 3% от `R_MAX`.
6. «Прокруст»: раскладка, повёрнутая на 90° и отражённая, после выравнивания
   совпадает с исходной с невязкой ниже порога.
7. «Нет наложений»: минимальное попарное расстояние ≥ сумма радиусов.

**Аутентификация:** валидный initData проходит; подменённый хоть на один символ — не проходит;
`auth_date` 25-часовой давности — не проходит.

**Связи:** нельзя связаться с собой; повторная связь даёт `409`; `(a,b)` и `(b,a)` —
одна и та же строка; удаление пользователя убирает его рёбра.

**Приглашения:** повторное использование токена не создаёт дубль; принятие собственного
приглашения не создаёт петлю; чужие `pending` не попадают в `GET /api/graph`.

Скрипт `npm run seed:demo` — генерирует 80 тестовых пользователей с реалистичной структурой
(3 плотных комьюнити, 2 хаба-связки между ними, десяток одиночек) для проверки картинки
глазами.

## 14. Безопасность и лимиты

- Все админские маршруты проверяют членство в `ADMIN_TELEGRAM_IDS` на сервере.
- Rate limit по id пользователя (in-memory, окно 1 мин): `POST /api/invites` — 10,
  `POST /api/links` — 30, `PATCH /api/me` — 20, остальные POST/PATCH/DELETE — 60.
- Имена: очистка от управляющих и zero-width символов **при сохранении**, не при выводе.
  На клиенте текст рисуется в canvas — XSS там невозможен, но в админке (DOM) имена
  выводить только как текстовые узлы, никакого `innerHTML`.
- Токены приглашений: 16 случайных байт из `crypto.randomBytes`, base64url.
- Сравнение всех секретов — `timingSafeEqual`.
- В логах не печатать `initData`, токен бота и содержимое сессионных кук.
- CORS: запросы идут с того же origin, что и страница, поэтому CORS-мидлвары быть не должно
  вообще. Если она всё же понадобится — разрешён строго `https://kvadratnikitosa.ru`,
  и только он.
- Кука ограничена `Path=/galaxy`: соседние приложения домена (`/`, `/bankiru`) её не видят.
- `helmet` с настройкой CSP, разрешающей `frame-ancestors https://web.telegram.org
https://*.telegram.org` и скрипт `https://telegram.org/js/telegram-web-app.js`.

## 15. Деплой

Повторяет схему соседнего проекта `kvadrat` на том же сервере: локальная сборка → `rsync`
готового `dist` → `npm install` и `pm2 startOrRestart` на сервере. Ничего не собирается
на VPS, кроме установки зависимостей и применения миграций.

### 15.1. Раскладка на сервере

```
/root/dev/galaxy/
  ├── avatars/                  # ВНЕ dist: переживает деплой, в rsync не участвует
  └── dist/
      ├── server/               # скомпилированный сервер (tsc)
      ├── shared/               # общий код, включая config.ts с BASE_PATH
      ├── public/               # собранный клиент (vite build с base: '/galaxy/')
      ├── prisma/
      │   ├── schema.prisma
      │   └── migrations/       # нужны на сервере: там выполняется migrate deploy
      ├── package.json
      ├── package-lock.json
      ├── ecosystem.config.cjs
      ├── .env                  # создан вручную, в rsync не участвует
      └── node_modules/         # ставится на сервере через npm, не заливается
```

Из rsync исключены и **не удаляются** `--delete`: `node_modules`, `.env`, `.DS_Store`.
Каталог `avatars/` лежит уровнем выше и в область синхронизации не попадает вовсе.

### 15.2. Prisma на сервере

`node_modules` живёт на сервере, а `@prisma/client` без кодогенерации нерабочий. Отсюда
два обязательных условия, иначе процесс упадёт на старте с `@prisma/client did not initialize yet`:

1. Пакеты `prisma` и `@prisma/client` — в `dependencies`, **не** в `devDependencies`:
   деплой ставит зависимости с `--omit=dev`, и из `devDependencies` CLI на сервер не попадёт.
2. В заливаемый `package.json` подставляется `"postinstall": "prisma generate"` — клиент
   генерируется на сервере сразу после `npm install`.

Миграции применяются отдельным шагом до перезапуска: `npx prisma migrate deploy`.
Никогда не `migrate dev` и не `db push` на проде.

### 15.3. `deploy/ecosystem.config.cjs`

Расширение `.cjs` обязательно: рядом `package.json` c `"type": "module"`, обычный `.js`
pm2 не загрузит через `require`.

```js
module.exports = {
	apps: [
		{
			name: 'galaxy',
			script: 'server/index.js',
			cwd: '/root/dev/galaxy/dist',
			instances: 1,        // строго 1: таймер раскладки и воркер outbox не кластеризуются
			exec_mode: 'fork',
			autorestart: true,
			max_restarts: 50,
			min_uptime: '10s',   // падает сразу после старта — не молотить рестартами
			restart_delay: 2000,
			max_memory_restart: '400M',
			time: false,
			env: { NODE_ENV: 'production' },
		},
	],
};
```

Один инстанс — требование архитектуры, а не экономия: пересчёт раскладки (7.8) и воркер
рассылки (12) держат состояние в памяти процесса, при нескольких копиях они начнут
дублировать работу и слать людям по два сообщения.

Порт 3005 берётся из `.env`, в конфиг pm2 его не дублировать.

### 15.4. `deploy.sh`

Написать по образцу `deploy.sh` проекта `kvadrat`: те же флаги, тот же стиль вывода,
тот же `set -euo pipefail`.

```
./deploy.sh              собрать клиент + сервер, залить, накатить миграции, перезапустить
./deploy.sh --setup      разовая настройка: pm2, автозапуск, PostgreSQL, каталог avatars
./deploy.sh --migrate    только накатить миграции
./deploy.sh --logs       живые логи (pm2 logs, через ssh -t, иначе Ctrl+C не дойдёт)
./deploy.sh --status     что крутится на сервере
./deploy.sh --restart    перезапустить, ничего не собирая
./deploy.sh --no-build   залить уже собранное
./deploy.sh --dry-run    показать, что бы залилось
```

Параметры:

```bash
REMOTE="${GALAXY_REMOTE:-root@193.124.203.221}"
REMOTE_DIR="${GALAXY_REMOTE_DIR:-/root/dev/galaxy/dist}"
APP_NAME="galaxy"
REMOTE_ENV='export NVM_DIR="$HOME/.nvm"; [ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh";'
```

Порядок обычного прогона:

1. `npm run build` в `web/` (Vite, `base: '/galaxy/'`) и `npm run build` в `server/` (tsc,
   `server/dist` предварительно сносится — от прежних раскладок могут остаться лишние файлы).
2. Проверки перед заливкой, каждая с внятной ошибкой: есть `web/dist/index.html`;
   есть `server/dist/server/index.js`; есть `server/dist/shared/config.js`;
   **в `web/dist/index.html` ссылки на ассеты начинаются с `/galaxy/`** — эта проверка
   ловит забытый `base` до того, как прод отдаст белый экран.
3. Сборка посылки в `.deploy/`: `server`, `shared`, `web/dist → public`, `prisma`,
   `ecosystem.config.cjs`, `package-lock.json` и `package.json` с подменёнными
   `scripts.start = "node server/index.js"` и `scripts.postinstall = "prisma generate"`.
4. `rsync -az --delete` с перечисленными исключениями.
5. `npm install --omit=dev --no-audit --no-fund` на сервере.
6. `npx prisma migrate deploy` на сервере.
7. `pm2 startOrRestart ecosystem.config.cjs --update-env && pm2 save`.
8. `pm2 logs galaxy --lines 15 --nostream` и финальная строка
   `Готово: https://kvadratnikitosa.ru/galaxy`.

Шаг 6 обязан идти **до** шага 7: перезапускать процесс на непринятой схеме бессмысленно.
Если `migrate deploy` упал — прерваться, не трогая pm2; старая версия останется работать.

`--setup` делает разово: ставит pm2, если его нет; разворачивает PostgreSQL с нуля,
заводит роль и базу `galaxy`, проверяет подключение и то, что порт не смотрит наружу
(раздел 2.6); заводит крон резервного копирования; создаёт `/root/dev/galaxy/avatars`; включает
`pm2 startup systemd -u root --hp /root`; напоминает создать `.env` руками и
показывает его шаблон. Чужие процессы (`kvadrat`, `bankiru`) не трогает ни при каких флагах.

## 16. Критерии приёмки

Работа принята, когда всё перечисленное воспроизводится вручную на проде
(`https://kvadratnikitosa.ru/galaxy`):

1. Открытие Mini App из Telegram логинит без единого действия пользователя; подделанный
   initData получает `401`.
2. Новый пользователь видит экран профиля с предзаполненным именем из Telegram; поля
   возраста и пола пусты; «Пропустить» работает.
3. Имя без `customName` и без имени в Telegram падает на `@username`, а без username — на id.
4. «Позвать друга» отдаёт ссылку и готовый текст; кнопка открывает нативный шеринг Telegram.
5. Тусклая точка видна только пригласившему; второй пользователь на своём небе её не видит.
6. Переход по ссылке-приглашению зажигает звезду **без** дополнительных подтверждений,
   пунктир превращается в сплошную линию, пригласившему приходит сообщение от бота.
7. «Связать» на чужой звезде создаёт связь мгновенно; «Развязать» её убирает; обе стороны
   видят изменение после следующего обновления графа.
8. Граф-звезда из 1 хаба и 12 листьев ставит хаб в центр. Два таких хаба расходятся
   симметрично, центр карты оказывается между ними. Проверяется на сид-данных.
9. Повторный вход даёт то же самое небо — звёзды на тех же местах, картина не перевёрнута.
10. Женские звёзды заметно теплее мужских при прямом сравнении, но общее небо остаётся
    серебристо-белым, а не «синим и розовым».
11. Наведение (десктоп) и тап (мобильный) показывают карточку в углу с аватаркой, именем
    и кнопкой «Связать»/«Развязать».
12. 200 узлов и ~500 рёбер: ≥ 55 fps на ноутбуке и ≥ 30 fps на телефоне трёхлетней давности.
13. Админка позволяет: создать тестового пользователя, переименовать любого,
    удалить любого, вручную создать и удалить связь, запустить полный пересчёт.
14. После админского переименования пользователь не может вернуть себе прежнее имя.
15. Удаление пользователя убирает его звезду и все его линии, небо пересчитывается плавно.
16. `npm test` проходит целиком.
17. Приложение открывается по `https://kvadratnikitosa.ru/galaxy`; во вкладке Network
    ни один запрос не уходит выше префикса `/galaxy/`; перезагрузка страницы на любом
    внутреннем маршруте (например `/galaxy/admin`) отдаёт приложение, а не 404.
18. `https://kvadratnikitosa.ru/` и `https://kvadratnikitosa.ru/bankiru` работают как
    прежде; в `pm2 list` три процесса, все `online`.
19. `./deploy.sh` проходит от начала до конца на чистой машине разработчика и заканчивается
    рабочим прод-сервисом; повторный запуск не стирает аватарки и `.env`.
20. В `package.json` и в `node_modules` на сервере нет `zod`; валидация тел запросов
    сделана функциями из `lib/validate.ts`.
